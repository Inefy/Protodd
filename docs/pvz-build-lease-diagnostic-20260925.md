## Offline builder geometry

`training/pvz_build_geometry_review.py` verified the archived log hashes from both reviewer reports and matched Pylon lease ends with the preceding sampled `ENTITY` positions. Across 27 reference and 21 candidate Pylon hard releases, **every** chosen builder had at least one closer visible Probe at the sampled issue time. The median selected-builder distance to the Pylon center was 1,112 pixels in the reference and 997 in the candidate; the nearest other visible Probe medians were 501 and 247. This is a proximity observation, not a claim that those Probes met `findBuilder`'s interruptibility, threat, lease and `canBuild` filters. The closest other Probe was itself in `PlaceBuilding` for 20/48 cases, which reinforces that distinction.

The travel extension shifted where the order ended: only 1/27 reference hard releases had the selected Probe within 128 pixels of the site, compared with 17/21 candidate releases. The site was still reported buildable for the selected Probe with a path in 47/48 hard-release records. At issue time, `build()` chooses a Probe using either the starting location for an emergency Pylon or the plan rally point, then `buildLocation()` chooses a tile; it does not select a second builder near the chosen tile. This ordering can explain the distance gap, but the archived logs cannot establish that a closer *eligible* Probe existed. A next observation-only diagnostic should invoke the exact `findBuilder` filters with the chosen site as the anchor, then log that alternative's distance, path and `canBuildHere` result. ## Final-approach review and revised mechanism

`training/pvz_build_approach_review.py` independently verified the archived reference and longer-lease candidate log hashes, recorded the Pylon builder's 24-frame position samples from issue through lease end, and pinned both bridge source hashes. The read-only result is `build/pvz-build-lease-review-20260925/approach-v2.json`. All 16 candidate hard releases in the 97–128-pixel band still had native order `PlaceBuilding`, the requested build type, and position progress within the previous four frames. Fifteen released at 124–127 pixels. All 16 had closed by at least 16 pixels in the last 96 frames; none was sampled within the retry guard's 96 pixels. Fifteen of 16 had `canBuildHere` for the worker and `hasPath` at release. These are live diagnostic observations from a failed candidate, not a validated strength effect.

The archived candidate policy extends the Pylon lease **only while distance is over 128 pixels**. Its archived native boundary test explicitly expects extension at 129 pixels and no extension at 128. After the original eight-second deadline, crossing 128 immediately makes `travellingPylon` false and enters the hard-release branch. That branch attempts `Stop` for a still-active Pylon build command. Thus the pileup at 124–127 pixels is a policy boundary effect, not evidence that Probes orbit a blocked footprint. The observations do not establish whether the same orders would have completed if allowed to continue. Separately, `build()` returns `build-command-in-progress` when its last command and build type still match the pending order; those 16 orders never reach the non-Nexus exact-site retry guard. Widening the retry radius alone cannot address them. The earlier suggestion to test a 97–128-pixel retry is superseded by this control-flow finding.

Next test the hard-release transition itself in a controlled native policy scenario and, if needed, add observation-only boundary telemetry to distinguish an active approach from a blocked final placement. Any correction must preserve a bounded escape for truly stalled or invalid footprints and pass a frozen functional screen before repeated independent-seed live evaluation. Do not restore the rejected blanket 18-second travel rule or infer wins from frame-capped games. Working gameplay source remains the observation-only builder-selection diagnostic, with `BwapiBridge.cpp` SHA-256 `13500de2e875a8946605fe06517cb20010cc57b45bca13dcfd5e6ab85047a1e4`.
